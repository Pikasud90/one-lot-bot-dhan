# US-003 — Telegram client and compact alert formatter, with redaction hardening

## Story
As the owner, I want each alert rendered as a short unambiguous phone message and sent by a safe Telegram client, so that I can act from my phone without opening the app and my bot token can never leak.

## Acceptance criteria
- AC1: Given an alert dict, when format_alert(alert, now) runs, then it returns Telegram HTML of at most 12 lines (split on newline) and at most 600 characters of the final HTML, with the line template: header action word and instrument (BUY or SELL, for index BUY plus CE or PE and strike); unit (1 share or 1 lot (N)); entry tagged mkt for stocks and live-chain ask, est. for synthetic; for index alerts the underlying stop and target plus the premium; stop and target (the word trail when none); strategy name and timeframe; confidence as NN plus label; TTL as an absolute IST deadline plus floored minutes left (or expired when 0 or less); data source tagged live or delayed ~15m taken from data.delayed (the single rule from US-028, never re-derived from data.source); alert time as HH:MM:SS IST; first six characters of the alert id; over budget the label is truncated with an ellipsis and never mid-entity or mid-tag; tags are balanced and only b, i, code; golden-text tests cover stock BUY, stock SELL, index CE with a live-chain premium, index PE with a synthetic premium, and no target.
- AC2: Given dynamic text with angle brackets, ampersands, a newline or emoji (instrument M&M, a label containing a tag), then everything is HTML-escaped and newlines inside a field are collapsed; and given an alert dict carrying account fields (balance, holdings, ledger, token), then none appear in the output because the formatter reads a whitelist of fields and ignores everything else (sentinel-value test).
- AC3: Given a TelegramClient, when send_message(text, silent=False) is called, then it POSTs sendMessage with parse_mode HTML and disable_notification sent iff silent; HTTP 200 with ok true and a message_id returns SendResult ok; HTTP 429 returns kind rate_limited with retry_after from parameters.retry_after (None when absent); 400, 401, 403 and 404 return kind permanent; 5xx, a network error, HTTP 200 with ok false, a non-JSON body or a missing message_id return kind transient; an unavailable client returns kind unavailable and makes no HTTP call; every request carries a 10 second timeout on all four httpx phases; the client itself never retries.
- AC4: Given a token shaped like 123456789:AAH-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx and five failure modes (connect error whose message holds the URL, HTTPStatusError, non-JSON body, timeout, bad JSON), then none of the full token, the string bot plus token, the part after the colon, or the percent-3A form appears in any SendResult field, exception text, repr or str of the client, or any DEBUG log record captured on a handler WITHOUT the global filter (the redactor is attached to the httpx logger itself and httpcore stays at WARNING or above); SendResult.detail is built only from the HTTP status and Telegram description, never from str(exc); the token lives in a private attribute with a masked repr; the three token forms are registered with the redactor and the chat id is NOT registered (it would corrupt numbers in logs).
- AC5: Given configuration, then the token must match ^[0-9]{6,12}:[A-Za-z0-9_-]{30,}$ and the chat id ^-?[1-9][0-9]{0,18}$ (ASCII only: a leading space, plus sign, zero, full-width digits and @channel are rejected); from_env strips CR and LF; a missing or invalid value makes available False with a human-readable unavailable_reason that never echoes the token; TELEGRAM_BOT_TOKEN and TELEGRAM_CHAT_ID are added to ENV_KEYS and secret_values, and Secrets.masked reports the Telegram token only as set or not set (never the last four characters).
- AC6: Given the suite runs, then no real network call is made (httpx.MockTransport plus an autouse socket guard), and format_exit(event, now) (at most 4 lines: EXIT label, reason, estimated P&L, time) and format_missed(alert, now) (one line) exist with golden tests for the Desk EXIT payload shape {advice, position}.

## Non-functional requirements
**2026-11-01T13:57+05:30**
- 10 s total timeout; thread-safe (16 concurrent send_message calls in a test); no retries in the client (the outbox owns them).
- Telegram limits: message under 4096 chars (we stay under 600); callers pace at 1 message/s per chat.
- New module fully type-hinted and mypy-clean under the US-000 ratchet; coverage at least 80 percent; hypothesis tests for length budget, escaping and redaction; no order-verb identifiers.
- Estimate: three independent estimates gave 3, 5 and 5; the redaction hardening is the real work.

## Public contract
**2026-11-01T13:57+05:30**
```python
# src/onelot/notify/telegram.py
def format_alert(alert: Mapping[str, Any], now: datetime) -> str
def format_exit(event: Mapping[str, Any], now: datetime) -> str            # event = Desk EXIT payload {"advice": str, "position": {...}}
def format_missed(alert: Mapping[str, Any], now: datetime) -> str
@dataclass(frozen=True) class SendResult:
    ok: bool; kind: Literal["ok","rate_limited","permanent","transient","unavailable"]; message_id: int | None; retry_after: float | None; detail: str
class TelegramClient:
    def __init__(self, token: str, chat_id: str, http: httpx.Client | None = None) -> None
    available: bool; unavailable_reason: str | None
    def send_message(self, text: str, *, silent: bool = False) -> SendResult
    @classmethod
    def from_env(cls, env: Mapping[str, str] = os.environ, http: httpx.Client | None = None) -> "TelegramClient"
# redaction: onelot.logging_setup.register_secrets(...) receives the three token forms; a logging.Filter is attached to the "httpx" logger
```
