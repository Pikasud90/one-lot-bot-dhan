# US-004 — Alerts reach Telegram through a durable outbox

## Story
As the owner, I want every SIGNAL, EXIT and CRITICAL notification delivered to my phone reliably through a durable queue, so that I never silently lose an alert even across restarts and outages.

## Acceptance criteria
- AC1: Given Telegram is configured, when a Notification of level SIGNAL is sent, then TelegramChannel.send performs ONE short INSERT (no HTTP, no Notifier call-back) of a telegram_outbox row with status queued, and in a fake-transport test the row exists with status queued when the HTTP handler runs; after the response the row records message_id, sent_at from the injected clock and latency_ms = round((sent_at minus alert_created_at) in ms) clamped at zero; p95 is nearest-rank over the last 100 sent.
- AC2: Given a 429 with retry_after 3, then next_attempt_at = now + max(retry_after, 1) and drain_once returns without sleeping; the only sleep enforces 1.000 s spacing between sends measured on the fake clock; transient failures retry after min(60, 2^(attempts-1)) seconds without jitter and until expires_at; given now at or after expires_at, then the original is marked skipped and ONE missed note per alert is enqueued, and after a long outage a single digest is sent instead of N notes.
- AC3: Given the worker, then it claims a row with UPDATE ... WHERE status is queued, commits, makes the HTTP call and only then updates; rows found in sending at startup are re-queued once and prefixed with a resend marker (at-least-once, ADR-002); at most one row exists per (alert_id, kind); a duplicate enqueue returns True and is not a channel failure; starting the worker twice is a no-op; Engine.stop stops and joins it before db.dispose.
- AC4: Given the Notifier, then Notification carries kind and dedup_key (set by Notifier.send from signal_id, position_id and level), channels may define accepts(n) so only SIGNAL, EXIT and CRITICAL reach Telegram while INFO, WARNING and the self-test never do, add_channel and replace_channel work under the Notifier lock and create the stats entry (no KeyError), status() merges each channel own status(), and stats count a message as sent only when Telegram confirmed it (enqueued is a separate count).
- AC5: Given an EXIT advice that persists while the desk re-evaluates every poll, then the phone gets the first EXIT immediately and at most 3 reminders at 5 minute intervals while the position stays open, never one message per poll.
- AC6: Given a permanent failure (400, 401, 403, 404), then the row is failed with the scrubbed detail and no endless retry occurs, and the dashboard and OS-toast channels still deliver the same alert; given an enqueue that raises, then the Notifier result is {dashboard: True, telegram: False} and nothing else breaks.
- AC7: Given the queue holds more than 8 messages, then the top 8 by confidence go individually at 1 message/s and the rest as one digest; messages are formatted at send time so time-left is never stale; p95 alert-to-sent is at most 10 s when 8 or fewer are queued.

## Non-functional requirements
**2026-11-01T13:57+05:30**
- Threading (ADR-002 amendment 6): the worker never takes the desk lock, never calls the Notifier, no transaction spans an HTTP call; the desk poll already holds its RLock during notifier.send (existing OS-toast subprocess under that lock — tracked as US-026), so TelegramChannel.send must be a single short INSERT.
- SQLite is single-writer: batch writes, short transactions; tests use a FILE-based tmp sqlite (threads), a fake clock and a fake sleep — no real sleeping, no wall-clock assertions.
- Config: add the new NotifyCfg fields (telegram_levels, telegram_quiet_outside_session) in the model BEFORE the YAML (Strict). The stale "not implemented" warning is removed.
- No order-verb identifiers; no real network; the token never appears in outbox rows, status JSON or logs.
